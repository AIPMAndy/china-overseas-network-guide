# 22｜7 天稳定性 SLO：从“能用”变成工程验收

**本章结果：**得到一份可复核的测量表，知道“稳定”是否适合你的业务场景。

## 定义三个层级

- **L0 连接建立**：连接/握手成功，并能得到预期路由。
- **L1 真实任务**：目标服务能够在合理时限内执行，例如完成一次合法的 API 测试、Git 拉取或会议连接。
- **L2 业务不中断**：主用失败后，切换到备用方案恢复核心任务，并能回退到正常网络。

## 对所有网络方法一视同仁

在 **3 种时段 × 7 天 × 2 种接入网络** 记录 42 个测试点。分开统计家庭宽带和手机热点；仅在适用时测试 eSIM/漫游。每次都记录：连接成功、目标应用成功、耗时、DNS/IPv6 状态、出口变化、故障原因、恢复时间。

### 推荐但非行业标准的个人 SLO 例子

- 核心任务成功率 ≥ 95%，测量分母完整报告，不能删掉失败样本。
- 关键页面响应耗时 p95 ≤ 8 秒；会议/实时控制需要另外制定更严格标准。
- 恢复时间 RTO ≤ 10 分钟；超过立即启动可控应急方案。
- 主备至少应当有**不同上游/服务商或接入介质**，不能只有同 VPS 两个协议。

## 把“高峰不稳定”量化

如果下午 16:00—24:00 表现差，必须和非高峰时段分别统计；不能只报告夜间 02:00 的测速。无法取得完整样本时就写 `n<42`（此处仅是示例规定，最终口径在附录中说明），不得写“全国可用率 99%”。

## 两次故障演练

1. **主出口不可用演练**：人为断开授权的主用连接，记录备用方案上线时间与任务结果。
2. **本机配置回滚演练**：关闭 TUN/系统代理，确认微信、银行、内网/NAS、国内服务恢复正常。

## 失败后的选择

- 失败集中在同一**接入网络**：优先研究本地运营商/接入路径与 UDP/IPv6 差异。
- 失败集中在同一**服务商/服务器**：优先审查上游和服务器资源。
- 失败集中在同一**目标应用**：优先审查应用侧策略和 DNS/账号条件。

所有推断都是待进一步验证的假设，变更一次只动一个因素。填写 42 行的 [七天测量表](../templates/七天测量表.csv) 后，可在项目根目录运行 `python3 tools/slo_report.py templates/七天测量表.csv`。脚本只统计明确填写 `0` 或 `1` 的记录，并按接入网络分组；空白不会被当作成功或失败。完成结果记录在 [七天测量表](../templates/七天测量表.csv) 和 [网络方案观察表](../templates/网络方案观察表.csv)。
