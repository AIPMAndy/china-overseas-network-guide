# 06｜稳定性：别看测速截图，先定义指标

**本章结果：**能够用七天的证据判断方案是否适合自己，避免“今天打开了 Google 就说永久稳定”。

## 一、四个维度

1. **连接成功率**：按固定采样时间，成功建立连接的次数 / 尝试次数。
2. **目标服务可用率**：连接已建立的情况下，真实工作服务按时响应的次数 / 总访问次数。
3. **时延分布**：p50（中位数）与 p95（95% 分位数）比一次测速平均值更有参考意义。跨境网络更容易受到高峰拥塞影响。
4. **恢复能力**：一次中断从发现到恢复需要几分钟？主用不可用时能否切到备用？DNS/代理有没有残留？

**注意口径**：请区分“无法连接”“目标网站本身故障”“访问延迟过高”“成功但慢”。样本量太少，只能叫初步记录，不足以推断全年稳定性。

## 二、一个可以自行修改的验收标准

下面是**演示阈值，不代表行业标准或真实实测数据**。你可以按工作任务重新设定：

| 指标 | 示例标准 | 如何记录 |
|---|---|---|
| 关键站点成功率 | ≥ 95% | 每天 3 个时段 × 7 天，每次记录成功与否 |
| 连接建立耗时 | 大多数尝试 ≤ 15 秒 | 手机秒表/客户端状态；关键看长尾 |
| 关键页面响应时间 | p95 ≤ 8 秒 | 同一网址，标准化测试网络 |
| 失败后恢复时间 | ≤ 10 分钟 | 记录首次失败和恢复时刻 |
| 备用方案 | 7 天中至少演练 2 次 | 从主用断开到备用正常使用 |

选择测试时段如 **09:00、15:00、21:00（北京时间）**；这只是固定采样例子，要尽量包含你实际工作时段。每个时段至少测两项你真正需要的功能：例如 GitHub 页面和具体文档/API。不要把不同设备、不同运营商数据混成一个看似漂亮的平均值。

## 三、第一次连接后照这个顺序验收

1. **基础网络**：不开客户端，也能访问正常国内网络吗？不能则先修本地宽带。
2. **客户端**：服务端/客户端状态是否连接；设备是否有正确权限？
3. **HTTPS**：访问目标站点时浏览器没有证书错误，不出现异常重定向。
4. **DNS**：通过系统工具检查当前解析器与客户端设置一致；**单一 DNS 检测网站不能证明所有应用没有 DNS 泄漏**。
5. **IPv6**：记录本地是否启用 IPv6，确认它的路由是否符合你的预期；不要随便关闭全系统 IPv6 作为“万能修复”。
6. **应用层**：浏览器、终端、真正使用的 App 分别测试。
7. **切换/回退**：关闭客户端后，是否留下不可达的系统代理或 DNS 设置。

## 四、主备线路该怎么设计

**两个节点不等于两条独立备份。**如果它们都在同一家供应商、同一个数据中心、同一种接入方式，可能一起失败。主备最好分开供应商/机房/网络路径，且均有合法使用依据。优先采用有明确管理、合同和技术支持的方案。

备份策略只需要回答四句话：“主用是什么？出现什么条件切换？备用是什么？失败后如何退回正常网络？”把它写到 [回滚卡](../templates/应急回滚卡.md)，每周演练一次。

**完成凭证：**至少有 [7 天观测表](../templates/七天测量表.csv) 和一份“通过/不通过 + 原因”的结论。
