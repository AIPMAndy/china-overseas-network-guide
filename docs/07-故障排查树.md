# 07｜排障树：网络坏了，按这个顺序查

**本章结果：**不再遇到问题就立刻换服务器、重装系统或发送含密钥的日志。

## 第 1 关：断开客户端，本机能否正常上网？

- **不能**：检查 Wi‑Fi/网线/蜂窝数据、路由器、运营商；暂停处理 VPN。尝试另一个普通 HTTPS 站点，确认不是单一网站宕机。
- **可以**：继续检查客户端。记录故障起始时间、设备、网络，别先改十项设置。

## 第 2 关：客户端是否已经成功建立连接？

- **未连接**：查看输入的是不是受支持的格式、密钥是否过期/撤销、系统 VPN 权限、客户端版本；连接错误日志应先脱敏。
- **显示已连接**：继续第 3 关。界面显示已连接并不等于目标网站可用。

## 第 3 关：同一服务端，在另一台设备/另一种网络是否能用？

| 对照 | 更值得排查的方向 |
|---|---|
| 相同服务端，Mac 不行、手机行 | Mac 客户端、系统代理、DNS、权限、企业安全软件 |
| Mac 家宽不行、手机热点行 | 家宽链路、路由器、DNS 或运营商路径差异 |
| 两台设备 + 两种网络都失败 | 服务端状态、机房链路、密钥/协议统一问题（仍需验证） |
| 只有一个网站失败 | 目标服务、账号限制、HTTPS、分流规则，先排除网站侧问题 |

注意：上表是**优先排查方向，不等同于已经确定原因**。

## 第 4 关：若你维护自己的 VPS，检查什么？

只在有授权的机器上操作。以下是**只读检查**示例，可先在云控制台确认运行状态：

```bash
# 系统状态与资源
uptime
df -h
free -h

# 服务监听的本机端口（输出可能含内网地址，公开前脱敏）
sudo ss -lntup

# 检查防火墙状态（依系统选择其一；只读）
sudo ufw status verbose
sudo nft list ruleset

# 查看近 20 条系统关键消息（可能敏感，不直接公开）
sudo journalctl -p err -n 20 --no-pager
```

若存在服务端软件异常，依据 **对应项目官方文档**查进程与日志。不要把 `curl | bash` 当成所有问题的修复方法，尤其当服务器同时运行生产业务时。

## 第 5 关：DNS、IPv6、系统代理怎么定位？

- **DNS**：域名解析不到，但 IP 访问也可能涉及 TLS/SNI、证书与路由；不能单凭“换成某个公共 DNS”判断。诊断时比较系统 DNS、客户端策略与受控测试域名。
- **IPv6**：部分网络仅有 IPv6 或优先 IPv6，若隧道/分流覆盖不一致，结果会分裂。先记录和核对，之后选择正确、可回退的配置。
- **系统代理**：有些应用不遵循系统代理；有些只支持 HTTP(S) 或 SOCKS；终端还可能有环境变量。测试时要说清楚哪一个 App 走了哪一条路径。

## 第 6 关：什么情况下停止折腾？

连续 30 分钟无法确定根因、且改变配置会影响生产业务时，按回滚卡恢复正常网络；再单独排障。换机器前先看监测数据；如果是服务端被暂停、账单欠费或 SSH 凭据失效，换协议也不会解决问题。

## 五张截图就够排障（只提供脱敏版）

- 客户端名称与版本、操作系统及 CPU 架构。
- 连接状态及**遮住密钥/服务器地址**的错误文本。
- 云控制台显示实例运行/停止状态（账号、实例 ID、IP 打码）。
- 在不同网络下的同一目标服务测试结果。
- 执行过的步骤、哪一步开始异常。
