# 32｜稳定性不是感觉：监控面板、SLO、变更管理与月度复盘

## 一、必须分开统计四类数据

1. **网络层成功**：设备在线、授权客户端已建连接、DNS 与出口符合设定。
2. **应用层成功**：网页、Git、API 或会议在事先定义的时限内完成核心动作。
3. **业务层成功**：用户能交付工作，例如视频上传完成、代码提交完成、会议持续顺畅。
4. **恢复能力**：主方案失败后实际多少分钟能恢复任务；以及是否可安全退回国内普通网络。

只测第 1 项会产生“所有图标都是绿的，但没法工作”的假象。

## 二、设计最小监测计划

### 7 天观察

每天 3 个时段 × 2 种接入 × 7 天 = **42 个预设观测点**（不适用网络可提前标记，不可把缺失填成功）。记录设备、地点粗粒度、接入运营商、出口方案代号、目标任务、成功与否、响应时间、DNS/IPv6 是否异常。别将真实手机号、客户 URL、Token、订阅链接记入表。

### 每周复核

- 统计每项业务任务的成功样本 / 有效样本，另报告计划样本总数和缺失率。
- 延迟统计 p50/p95 时只对实际取得耗时的同类任务计算；失败样本单独报告，避免幸存者偏差。
- 区分基础 Wi-Fi 问题、上游/服务器问题、应用账号问题和区域服务限制。
- 看切换发生次数、误切次数和业务损失，不能只看成功率。

### 每月复盘

- 收费/运维工时/工单/停工损失总成本。
- 软件版本、密钥到期、服务商存续、是否需要更新或退出。
- 30 天内真正独立切换是否成功。没有演练证据时报告“尚未验证”。

## 三、建议 SLO（**自行定义的样例，不构成业内通用指标**）

| 业务 | 示例 SLO | 测量方法 | 失败代价 |
|---|---|---|---|
| 公开资料浏览 | 有效样本任务成功率 ≥ 95% | 页面成功打开并加载关键内容 | 可稍后重试 |
| 小额 API 开发 | 成功率 ≥ 98%，明确单次额度上限 | 固定低风险测试请求 | 额外成本与调试停滞 |
| 实时会议 | 每次会议人工记录卡顿/断音/掉线 | 真实会议记录，不只测 Ping | 沟通中断 |
| 内容上传 | 每个文件的成功完成率 ≥ 98% | 带大小和用时的成功上传事件 | 重传和发布延误 |
| 恢复能力 | RTO ≤ 10 分钟 | 断主线开始到完成业务任务 | 停工损失 |

样本小时数很少时，不应用“99.9% 年度稳定率”等宣传语。`成功率 = 已明确成功的有效样本数 / 明确成功或失败的有效样本数`，同时必须展示遗漏率；不同类型任务不要胡乱混算一个平均分。

## 四、把网络健康映射到业务决策

- **连续下降但仍可用：**优先保留已有会话、停止不必要的配置变更，晚些时候做 A/B 复测。
- **连接已断：**按 [28 章](28-主备线路与故障独立性.md) 先恢复业务；故障归因推迟到恢复后。
- **账号安全异常：**停止敏感操作，优先官方安全流程。不要通过换 10 条线路试图“刷掉异常”。
- **高成本/低可用性：**用 TCO 和任务成功率决定淘汰，而不是看广告评价。

## 五、变更前后必须比较

**任何变更都记录：**`日期 → 变更前版本/配置摘要 → 唯一改动 → 目标 → 测试网络 → 三任务结果 → 发现异常 → 回滚是否有效`。

每次最多改一个主要因素。更换节点、同时改 DNS、升级客户端和切换 TUN 会让失败原因无法辨认。**先建立“已知可用配置快照”，再做探索。**

使用现有 [七天测量表](../templates/七天测量表.csv) 和 `python3 tools/slo_report.py templates/七天测量表.csv`；月度报告模板见 [网络月度复盘](../templates/网络月度复盘.md)。
